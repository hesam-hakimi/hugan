# Safe Mode Foundation

Safe Mode is the first write-capable milestone of the Universal Coding Agent. It is intentionally limited to human-approved, structured text edits materialized inside an isolated Git sandbox.

It does **not** stage, commit, push, create or edit a pull request, merge, deploy, or modify the source checkout.

## Control flow

```text
Safe task + approved manifest + trusted test policy
    → immutable sandbox at approved base SHA
    → repository index
    → human scope approval interrupt
    → bounded StructuredEditProposal JSON
    → deterministic exact-anchor edit validation
    → deterministic edit materialization in sandbox
    → Git-generated canonical unified diff
    → deterministic materialized-diff validation
    → fixed-profile focused tests
    → independent reviewer
    → retain passing sandbox change or deterministically restore approved paths
    → final evidence report
```

The model is responsible for **what semantic text should change**. It is not responsible for Git patch syntax. `diff --git`, file markers, hunk headers, line counts, and context prefixes are generated by Git from the materialized sandbox state.

## Mandatory safety contracts

### Frozen repository identity

The approved change manifest contains an immutable `base_sha`. Safe Mode resolves the requested Git ref and blocks before implementation when the sandbox SHA does not match.

### Approved path manifest

Every allowed file is listed exactly once with one operation:

- `modify` for an existing regular UTF-8 text file;
- `create` for an absent UTF-8 text file whose parent directory already exists.

Safe Mode rejects deletes, renames, copies, symlink changes, binary edits, duplicate edit paths, path traversal, absolute paths, and changes under denied prefixes.

### Human scope approval

The graph always interrupts before invoking the implementer. Approval is bound to:

- base SHA;
- prior plan hash;
- canonical scope hash;
- exact allowed paths and operations;
- denied prefixes;
- fixed test profile IDs;
- acceptance criteria.

Resume requires the same LangGraph thread ID and state directory.

### Structured-edit implementation boundary

The model returns a typed `StructuredEditProposal`; it cannot directly write files or run commands.

A modify edit contains one or more exact replacements:

```json
{
  "path": "src/example.py",
  "operation": "modify",
  "replacements": [
    {
      "old_text": "exact existing text copied from the supplied base state",
      "new_text": "replacement text"
    }
  ],
  "content": null
}
```

Each `old_text` must occur exactly once in the approved base file. Multiple replacements in the same file must not overlap. A create edit supplies complete UTF-8 `content` and may target only an approved absent file with an already-existing parent directory.

The deterministic edit engine validates all anchors and all file operations **before any write**. It then materializes the edits in memory and writes only the approved paths inside the sandbox. If validation fails, no edit is written.

### Secret-safe context

Allowed file text is sanitized before it is sent to the model. If sanitization would change an approved file's visible content, the context compiler marks that file `CONTENT_REDACTED_FOR_SAFETY` instead of presenting altered text as an exact-edit source. This prevents a model from accidentally using redacted text as a supposedly exact replacement anchor.

### Tool-generated canonical patch

After structured edits are materialized, the control plane asks Git to generate the canonical unified diff. The model never authors or repairs patch syntax in the current protocol.

The generated diff is then checked against:

- the approved path and operation manifest;
- `max_changed_files`;
- `max_patch_bytes`;
- approved test-profile IDs;
- the frozen base SHA;
- actual sandbox `git status` paths;
- `git diff --check`.

The canonical patch remains an audit and review artifact even though it is no longer the model/tool boundary.

### Trusted focused-test policy

The model cannot invent shell commands. A trusted operator-owned policy maps profile IDs to exact argv arrays, working directories, timeouts, and bounded output limits. The approved manifest selects only profile IDs that exist in that policy.

### Independent review

The reviewer receives the original task, approved scope, the **tool-generated canonical Git diff**, focused-test evidence, exact changed paths, and post-change file state. A sandbox change is retained only when:

- scope was approved;
- structured edit validation passed;
- the canonical generated diff passed validation;
- all focused tests passed;
- no out-of-scope workspace change occurred;
- reviewer verdict is exactly `PASS`.

`PASS_WITH_CONDITIONS`, `BLOCKED`, `FAIL`, test failure, or any safety error triggers deterministic restoration.

### Deterministic rollback

Before materialization, Safe Mode writes a rollback checkpoint containing the base SHA, plan hash, scope hash, and exact changed paths. Rollback does not depend on model-authored or reverse-applicable patch syntax:

- approved `modify` paths are restored from `HEAD` with fixed Git argv;
- approved `create` paths are removed directly;
- no repository-wide reset or clean is performed.

## Why the structured-edit boundary exists

Earlier Safe Mode prototypes asked the model to emit raw unified diffs. Real-model qualification exposed an entire class of format failures: Markdown fences, malformed `diff --git` metadata, inconsistent path declarations, stale hunk context, and corrupt hunk syntax. Adding more patch-repair heuristics would have preserved the wrong abstraction.

The current design removes that failure class at the architectural boundary:

```text
Model semantic decision
    → exact structured edits
    → deterministic materialization
    → Git-generated patch syntax
```

Legacy raw-patch validation helpers remain temporarily in the codebase only for backward compatibility with persisted development artifacts and focused legacy tests. New Safe Mode graph executions do not invoke model-authored patch generation or patch-applicability repair.

## Scope manifest example

```json
{
  "manifest_version": "1",
  "base_sha": "0123456789abcdef0123456789abcdef01234567",
  "plan_hash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "allowed_changes": [
    {
      "path": "src/example.py",
      "operation": "modify",
      "purpose": "Implement the approved contract."
    },
    {
      "path": "tests/test_example.py",
      "operation": "create",
      "purpose": "Add deterministic contract coverage."
    }
  ],
  "denied_prefixes": [
    ".git",
    ".ssh",
    ".env",
    ".venv",
    "venv",
    "node_modules",
    "secrets",
    "credentials"
  ],
  "test_profiles": ["focused-tests"],
  "acceptance_criteria": [
    "The approved contract is implemented.",
    "Focused tests pass.",
    "No path outside the manifest changes."
  ],
  "max_patch_bytes": 200000,
  "max_changed_files": 16
}
```

## CLI

Start a Safe Mode task:

```bash
uca \
  --state-root /durable/state \
  --provider-factory package.adapter:create_provider \
  safe \
  --repository https://example.test/owner/repository.git \
  --ref feature/approved-base \
  --task-file task.md \
  --scope-file approved-scope.json \
  --policy-file trusted-policy.json \
  --task-id safe-task-001 \
  --thread-id safe-task-001
```

The first invocation pauses at `scope_approval`.

Inspect state:

```bash
uca --state-root /durable/state safe-status --thread-id safe-task-001
```

Approve and continue:

```bash
uca \
  --state-root /durable/state \
  --provider-factory package.adapter:create_provider \
  safe-resume \
  --thread-id safe-task-001 \
  --decision approve
```

Rejecting the scope produces a blocked final report without invoking the implementer.

For operator workflows, `scripts/safe-workflow.sh` persists run context so start/status/approve do not require manually reconstructing state identifiers.

## One-command local qualification

```bash
bash scripts/safe-smoke.sh
```

The smoke qualification proves:

- separate start and resume invocations;
- mandatory scope approval;
- immutable-base verification;
- exact path enforcement;
- structured edit materialization only in the sandbox;
- Git-generated canonical patch evidence;
- fixed-profile focused testing;
- independent review;
- source repository preservation;
- no new Git commit;
- final retained sandbox change on `PASS`;
- deterministic restoration on conditional review in unit coverage.

## Deliberate exclusions

Safe Mode Foundation does not provide:

- arbitrary shell access;
- package installation selected by the model;
- file deletion, rename, copy, binary, or symlink modification;
- staging or commits;
- push or pull-request operations;
- merge or deployment;
- automatic scope expansion;
- automatic approval of reviewer conditions;
- direct mutation of the source checkout;
- model-authored Git patch syntax in new Safe Mode executions.
